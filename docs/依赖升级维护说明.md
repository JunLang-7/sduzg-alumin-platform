# 依赖升级维护说明

GitHub 从默认分支 `main` 的 `.github/dependabot.yml` 读取配置；`dev` 保留相同配置。修改配置时同步两个分支。main 配置合并后，Dependabot 才能启用；仅合并 dev 配置不会启用机器人。

所有版本升级 PR 的目标为 `dev`，每周检查以下范围：

- `/server` 的 Go modules。
- `/web` 的 npm 依赖。
- GitHub Actions。
- `/server` 和 `/web` Dockerfile 的构建及运行镜像。

Go 与 npm 升级沿用按生态分组。提交前缀为 `chore(deps)`、`ci(actions)` 或 `build(docker)`，符合仓库提交标题要求。

## 处理升级 PR

1. 阅读机器人 PR 的依赖变更与发布说明，补充必要的验收证据。GitHub 记录的 PR 作者必须同时为 `dependabot[bot]` 且类型为 `Bot`，才豁免关联 Issue；普通 PR 仍需 `Closes #编号`。此豁免不依据分支名或 PR 标题，也不跳过 Linked issue 检查任务。
2. 验证提交标题、基础质量、安全扫描、集成测试和 E2E；出现破坏性变更时修复兼容性后再提交。
3. 保持人工评审、讨论解决和线性历史要求，通过后合并到 dev；发布仍由 dev 提交到 main。

机器人只提出升级 PR，不会自动合并。Go Docker 镜像升级不代表 `server/go.mod`、CI 固定的 Go 版本或项目文档已经同步更新；升级工具链时需逐项核对。漏洞扫描使用实时漏洞数据库，历史绿色 CI 不能保证当前依赖安全。

配置中的 `target-branch: dev` 用于版本更新，不能代替默认分支的 Dependabot 安全更新配置。默认分支的安全告警及安全升级仍需单独关注；当前已知漏洞需要及时处理，不能等待每周版本更新。

参考：[Dependabot 配置文件](https://docs.github.com/en/code-security/concepts/supply-chain-security/about-the-dependabot-yml-file)、[配置选项](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)。
