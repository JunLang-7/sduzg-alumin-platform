# 管理员数据变更审计与版本控制方案

版本：V0.1（评审稿）
日期：2026-09-05
适用项目：山大政管学院校友平台（MPA 试点）

## 1. 方案目的

本方案用于设计一套类似 Git 的“校友数据变更版本库”，解决以下问题：

1. 能够明确看到“谁”在“什么时间”修改了“哪个校友”的“哪个字段”。
2. 能够将一次保存操作拆成按字段的差异行，直观看到修改前和修改后。
3. 超级管理员能够按管理员、子管理员、时间、校友和字段筛选变更记录。
4. 超级管理员发现修改不合理时，可以只纠正指定字段，或者将指定版本中的字段恢复到修改前的值。
5. 所有纠正和恢复动作本身也产生新的版本记录，不能通过修改旧日志来掩盖历史。
6. 批量导入、删除、恢复、管理员资料修改等操作与普通手工编辑使用同一套审计模型。

本方案是产品和技术实现计划，不直接修改业务代码。评审通过后，再拆分为数据库迁移、后端接口、前端页面和测试任务。

## 2. 现状与需要补齐的能力

当前项目已有以下基础：

- 用户角色为 `alumni`、`admin`、`super_admin`。
- `alumni_profiles` 已有 `created_by`、`updated_by`、`created_at`、`updated_at`。
- 已有 `operation_logs` 表，可记录操作者、角色、动作、目标、详情、IP、User-Agent 和时间。
- 校友管理已有新增、编辑、删除、批量导入、导出和文件操作。
- 前端已有管理员管理页、校友管理页和统一的 Ant Design 表格风格。

现有能力与目标之间的差距：

| 当前能力 | 问题 | 本方案补齐方式 |
| --- | --- | --- |
| `operation_logs.detail` 保存 JSON | 只能知道发生过一次操作，不能稳定地按字段查询和分页 | 增加“变更提交 + 字段变更明细”模型 |
| 校友表只有 `updated_by` | 只能知道最后一次修改人，无法回看中间版本 | 为每个目标记录维护版本号和版本链 |
| 日志未覆盖所有校友 CRUD | 新增、编辑、删除、导入不能完整审计 | 所有写入路径统一接入变更服务 |
| `admin` 角色是平级的 | 无法表达主管理员、子管理员和管理关系 | 增加管理员上下级关系，不急于新增大量角色 |
| 没有差异页面 | 管理员需要打开详情页手工比较 | 增加按字段一行一条的差异表和时间线 |
| 没有安全恢复机制 | 直接覆盖当前数据可能误伤后续修改 | 采用“新纠正提交 + 乐观锁 + 冲突提示” |

实现时保留现有 `operation_logs` 作为兼容性和通用事件日志；新的字段级版本记录作为主要审计来源，不能仅依赖 `operation_logs.detail`。

## 3. 核心概念：用 Git 语言理解业务数据

这里借鉴 Git 的使用体验，但不把校友数据存进 Git 仓库，也不引入 Git 文件合并逻辑。校友档案是结构化数据库记录，版本控制应该在数据库事务内完成。

| Git 概念 | 本系统概念 | 说明 |
| --- | --- | --- |
| commit | 变更提交（change commit） | 一次成功的保存、导入、删除或纠正操作 |
| commit hash | 提交编号 | 面向用户展示的短编号，便于定位和沟通 |
| diff | 字段差异 | 一行表示一个字段的旧值和新值 |
| file | 业务目标记录 | 例如某一名校友档案、某个管理员账号 |
| history | 目标记录历史 | 同一校友所有版本按时间排列 |
| revert | 纠正/恢复 | 根据历史版本生成一笔新的反向变更 |
| branch / merge | 暂不实现 | 一期不做多人分支和自动合并，避免把数据审批复杂化 |

### 3.1 一次提交的边界

- 手工编辑一名校友并修改 3 个字段：生成 1 个提交、3 条字段差异。
- 手工编辑两名校友：生成 1 个提交、按目标记录和字段生成多条差异。
- Excel 批量导入：生成 1 个批量提交，下面挂载每条实际新增或修改的目标和字段差异；失败行不进入“已应用”差异。
- 删除一名校友：生成 1 个删除提交，保存删除前的必要快照，以支持后续恢复。
- 超级管理员纠正某次提交：生成 1 个新的纠正提交，引用原提交编号；原提交不可修改。

### 3.2 推荐的默认行为

本评审稿默认采用“立即生效、事后审计、超级管理员可纠正”的模式：

1. 子管理员保存后，数据立即生效。
2. 系统即时记录字段级差异。
3. 超级管理员在变更审计页发现问题后，可以查看差异并发起纠正。
4. 纠正不是删除或改写原记录，而是生成新的反向提交。

如果后续需要“子管理员修改后必须由超级管理员审批才能生效”，可以在此模型上增加 `pending` 状态，不需要推翻字段差异模型；该能力列为后续增强项。

## 4. 角色与管理员层级设计

### 4.1 角色定义

建议保留现有 `role` 值，使用关系字段表达上下级，不把每一种管理关系都硬编码成新角色。

| 身份 | `role` | 关系属性 | 默认审计权限 | 默认数据权限 |
| --- | --- | --- | --- | --- |
| 超级管理员 | `super_admin` | 根节点，可管理管理员关系 | 查看全部管理员、全部记录；可纠正全部数据 | 全部校友数据 |
| 主管理员 | `admin` | 无上级或由超级管理员直接管理 | 查看自己的变更；是否可看子管理员由配置决定 | 由数据范围决定，默认与当前一期一致 |
| 子管理员/副管理员 | `admin` | `parent_admin_id` 指向主管理员或授权管理员 | 查看自己的变更；不能查看其他管理员的敏感审计值 | 由上级分配的数据范围决定 |
| 校友 | `alumni` | 无管理员层级 | 不进入管理员审计后台 | 只能修改本人允许字段 |

“子管理员”和“副管理员”在产品文案上可以是同义词；数据库中建议统一使用 `sub_admin` 作为类型值，避免同时出现两个概念。

### 4.2 上下级关系规则

第一版建议只允许超级管理员维护管理员树：

1. 超级管理员创建管理员时，可选择“主管理员”或“子管理员”。
2. 创建子管理员时必须选择其直接上级。
3. 普通管理员不能创建、删除或提权管理员账号，保持现有一期边界。
4. 超级管理员可以调整子管理员的上级、停用子管理员或收回其数据范围。
5. 上下级关系变更也要生成审计提交，记录变更前后的上级和权限配置。
6. 删除管理员不删除其历史审计记录；历史记录显示“账号已停用/已删除”。
7. 防止环：不能把管理员设置为自己的下级，也不能形成循环上下级关系。

### 4.3 数据范围和字段权限

本方案将“管理员层级”和“能改什么数据”分开设计：

- 层级回答“谁管理谁”。
- 数据范围回答“能操作哪些校友”，例如全部 MPA、指定年级或指定班级。
- 字段权限回答“能操作哪些字段”，例如子管理员只能维护工作单位、职务和联系方式，不能修改姓名、年级和账号绑定。

MVP 可以先实现“全部校友 + 字段白名单”两种简单模式；当实际业务需要按年级、班级分工时，再增加数据范围规则。

## 5. 产品功能范围

### 5.1 变更审计页

建议新增管理后台页面：

`/admin/audit/changes`，中文名称为“变更审计”或“数据版本”。

超级管理员进入后默认看到全平台变更，普通管理员只看到自己有权查看的变更。

顶部筛选项：

- 时间范围。
- 操作者：姓名、账号、管理员类型。
- 管理层级路径：例如“超级管理员 / 主管理员 A / 子管理员 B”。
- 动作：新增、修改、删除、恢复、导入、纠正、管理员配置变更。
- 目标：校友姓名、校友 ID、管理员账号。
- 字段：姓名、年级、工作单位、手机号等。
- 来源：手工编辑、批量导入、校友本人修改、系统操作、纠正。
- 结果：已应用、部分冲突、已纠正、已恢复。

### 5.2 默认表格：一行一个字段变更

表格是本功能的主视图，不把一次提交压缩成难以比较的一行。默认一行代表一个字段变化：

| 提交 | 时间 | 操作者 | 目标对象 | 字段 | 修改前 | 修改后 | 来源/原因 | 状态 | 操作 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `C-8F31A2` | 2026-09-05 10:21 | 张三（子管理员） | 王某 / 2020级 | 工作单位 | 山东某单位 | 济南某单位 | 手工编辑 | 已应用 | 查看 |
| `C-8F31A2` | 2026-09-05 10:21 | 张三（子管理员） | 王某 / 2020级 | 职务 | 科员 | 副科长 | 手工编辑 | 已应用 | 查看 |
| `C-8F31A2` | 2026-09-05 10:21 | 张三（子管理员） | 王某 / 2020级 | 手机号 | `138****1234` | `139****1234` | 手工编辑 | 已应用 | 纠正 |

交互要求：

1. 同一提交的多条字段行使用相同提交编号，可点击进入提交详情。
2. 修改前和修改后都保留，空值统一显示为“空”。
3. 对敏感字段默认脱敏；只有具备相应权限时才允许临时查看明文，并记录查看行为。
4. 不仅依赖红绿颜色：同时使用“删除线、箭头、字段标签、状态文字”，保证可读性和无障碍。
5. 支持按“只看某个子管理员”“只看某个字段”“只看未处理/高风险变更”筛选。
6. 需要服务端分页、排序和筛选，不能把全部日志一次性加载到浏览器。

### 5.3 提交详情页/抽屉

点击提交编号后打开详情抽屉或详情页，内容包括：

- 提交短编号、完整 ID、创建时间。
- 操作者姓名、账号、角色、管理员层级路径。
- 动作类型、来源、备注/原因、请求 ID。
- 本次影响的校友数量和字段数量。
- 按目标对象分组的字段差异表。
- IP、User-Agent 等审计元数据（仅授权角色可见）。
- 是否由其他提交纠正、纠正提交的链接。
- “纠正本次提交”按钮。

提交摘要示例：

> `C-8F31A2` · 张三（子管理员）于 2026-09-05 10:21 修改 1 名校友的 3 个字段

### 5.4 单个校友的版本时间线

在校友详情页增加“变更历史”入口，按时间倒序显示：

```text
当前版本 v18    超级管理员    纠正 C-8F31A2    2026-09-05 11:03
       ↑
版本 v17        子管理员张三  修改工作单位、职务、手机号  2026-09-05 10:21
       ↑
版本 v16        主管理员李四  修改导师                  2026-09-04 16:40
```

时间线支持：

- 点击版本查看该版本相对上一版本的字段差异。
- 查看当前值、该版本值和修改前值。
- 仅勾选部分字段进行恢复，不默认整条记录回滚。
- 对已发生后续修改的字段显示冲突提醒。

### 5.5 管理员活动视图

在变更审计页提供“按管理员查看”视图：

- 管理员列表：总提交数、修改字段数、影响校友数、最近操作时间、被纠正次数。
- 管理员活动时间线：按日期显示其提交。
- 字段分布：该管理员最常修改哪些字段。
- 校友分布：该管理员主要操作哪些年级、班级或校友。
- 纠正率/冲突率：只作为管理参考，不直接作为处罚依据。

建议首版以数字卡片、柱状图和明细表为主；“一行一个字段”的差异表仍是事实来源，图表只做汇总。

### 5.6 子管理员管理页

扩展现有“管理员管理”页面，增加：

- 管理员树或层级路径。
- 管理员类型：主管理员、子管理员。
- 直接上级。
- 状态：正常、停用。
- 数据范围摘要。
- 字段权限摘要。
- “查看其变更”快捷入口。
- 超级管理员的“编辑权限/调整上级/停用”操作。

## 6. 超级管理员纠正流程

### 6.1 纠正单个字段

1. 超级管理员在字段差异行点击“纠正”。
2. 系统展示三列：修改前、当前值、修改后。
3. 默认建议恢复为修改前值，但允许超级管理员输入新的正确值。
4. 超级管理员勾选要纠正的字段，填写必填原因。
5. 后端检查当前版本是否仍与页面打开时一致。
6. 无冲突时，在同一事务内更新数据、递增版本号并写入新的纠正提交。
7. 页面显示“纠正成功”，并链接到新提交。

### 6.2 整次提交的反向恢复

当一次提交只涉及一个目标记录且风险较低时，可提供“反向恢复”。对于批量提交，默认不直接整批恢复，而是先展开目标和字段，让超级管理员选择范围。

反向恢复规则：

- 原提交的每一条字段变更生成一条反向字段变更。
- 原提交不变，状态显示“已被提交 C-xxxx 纠正”。
- 新提交的 `correction_of_commit_id` 指向原提交。
- 如果某字段在原提交之后又被其他人修改，不能静默覆盖，必须提示冲突。
- 纠正成功后，当前值以新提交为准，版本号继续递增。

### 6.3 冲突处理

示例：

```text
子管理员张三：工作单位 A → B       提交 C1
主管理员李四：工作单位 B → C       提交 C2
超级管理员准备恢复 C1 的旧值 A
```

此时系统必须提示：

> 当前值已不是该提交产生的值，直接恢复可能覆盖后续修改。请选择：查看最新差异、放弃恢复，或确认以超级管理员的新值覆盖。

即使超级管理员选择覆盖，也要生成新的纠正提交，不能修改 C1 或 C2 的历史数据。

## 7. 数据模型设计

以下为逻辑模型，字段名可在详细设计阶段根据现有数据库规范调整。

### 7.1 `change_commits`：变更提交主表

一条记录代表一次业务操作或一次批量操作。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 数据库主键 |
| `commit_id` | 对外展示的 ULID/UUID，稳定且不可预测 |
| `operator_id` | 操作者用户 ID |
| `operator_role` | 操作发生时的角色快照 |
| `operator_type` | 主管理员、子管理员、超级管理员等身份快照 |
| `manager_path` | 操作发生时的管理员层级路径快照 |
| `action` | create/update/delete/restore/import/correct/permission_change |
| `source` | manual/import/self/system/correction |
| `reason` | 操作原因或备注，可按策略要求填写 |
| `correction_of_commit_id` | 如果是纠正，指向原提交 |
| `request_id` | 关联 HTTP 请求 ID，便于排查 |
| `target_count` | 影响目标记录数 |
| `field_change_count` | 字段变化总数 |
| `status` | applied/partial/conflicted 等 |
| `created_at` | 提交时间 |
| `prev_hash` | 可选，上一条审计提交摘要 |
| `commit_hash` | 可选，当前提交摘要，用于防篡改校验 |

### 7.2 `change_items`：字段变更明细表

一条记录代表一个目标对象的一个字段变化，是“按行显示”的数据来源。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `commit_id` | 所属变更提交 |
| `target_type` | `alumni_profile`、`user` 等 |
| `target_id` | 目标记录 ID |
| `target_label_snapshot` | 目标展示名快照，避免账号删除后列表无法识别 |
| `field_name` | 稳定的内部字段名，如 `work_unit` |
| `field_label` | 当时的中文字段名快照，如“工作单位” |
| `data_type` | string/number/date/enum/json 等 |
| `old_value` | 修改前值，JSON 类型；敏感值加密存储 |
| `new_value` | 修改后值，JSON 类型；敏感值加密存储 |
| `is_sensitive` | 是否敏感字段 |
| `base_version` | 写入前目标版本 |
| `target_version` | 写入后目标版本 |
| `conflict_status` | none/detected/overridden 等 |
| `created_at` | 创建时间 |

不要把所有字段都作为自由 JSON 存储后再依赖前端猜字段含义；`field_name`、`field_label`、数据类型和敏感标记要结构化保存，便于稳定筛选、排序和权限校验。

### 7.3 `record_versions`：目标记录版本头

用于乐观锁和快速定位当前版本：

| 字段 | 说明 |
| --- | --- |
| `target_type` | 目标类型 |
| `target_id` | 目标 ID |
| `current_version` | 当前整数版本号 |
| `current_commit_id` | 产生当前版本的提交 |
| `updated_at` | 当前版本更新时间 |

`target_type + target_id` 建立唯一索引。`alumni_profiles` 建议增加 `data_version`；如果管理员账号也纳入版本控制，`users` 同样增加版本号。

### 7.4 管理员关系和权限表

建议先采用以下结构：

1. `users.parent_admin_id`：直属上级管理员 ID，可为空。
2. `users.admin_type`：`primary` / `sub_admin`；非管理员为空。
3. `admin_scopes`：管理员可操作的数据范围，例如全量、年级、班级。
4. `admin_field_permissions`：管理员可查看/编辑的字段白名单。

如果未来需要保留上下级关系的历史，可将关系独立为 `admin_relationships`，增加生效时间和失效时间；MVP 可以先在 `users` 保存当前关系，并将每次关系变化写入 `change_commits`。

### 7.5 敏感字段处理

以下字段至少按敏感字段处理：手机号、邮箱、通讯地址；具体清单可配置。

- 数据库存储：建议使用应用层加密后写入 `old_value` / `new_value`。
- 列表展示：默认脱敏，例如 `138****1234`。
- 明文查看：只对超级管理员或明确授权者开放，记录 `audit_value_view` 事件。
- 密码、密码哈希、JWT、验证码：禁止进入字段差异和操作详情。
- 导出审计：审计页面不默认支持批量导出明文敏感值；若后续需要，单独增加审批和水印。

## 8. 后端实现计划

### 8.1 新增统一变更服务

建议新增 `ChangeSetService` 或 `AuditChangeService`，不要让每个 handler 自己拼接日志。

服务职责：

1. 接收业务目标的修改前快照和修改后快照。
2. 根据字段白名单计算差异。
3. 对字段做敏感性判断和加密/脱敏处理。
4. 在数据库事务中写入提交主表和字段明细。
5. 递增目标版本并检查乐观锁。
6. 保存操作者、角色、层级、来源、原因和请求上下文。
7. 为纠正操作建立原提交关联。
8. 对无实际变化的保存不生成空提交。

推荐调用层次：

```text
handler
  -> service（校验权限、读取旧值、构造业务变更）
    -> repository transaction（更新业务表 + 更新版本头 + 写入 change_commits/change_items）
```

### 8.2 接入所有写入路径

| 写入路径 | 审计内容 |
| --- | --- |
| 管理员新增校友 | 所有初始字段：空 → 新值 |
| 管理员编辑校友 | 只记录实际变化的字段 |
| 管理员软删除校友 | 删除动作 + 删除前快照或可恢复字段 |
| 校友恢复 | 删除状态 → active，以及恢复原因 |
| Excel 导入 | 每行的新增、修改、跳过、失败状态；一个批量提交挂载多条明细 |
| 校友本人修改资料 | 记录允许修改字段；敏感联系方式按权限保护 |
| 管理员上传/删除文件 | 保留现有操作日志，同时可作为目标类型 `alumni_file` 接入提交模型 |
| 创建/停用/调整管理员 | 管理员账号字段、上下级、字段权限和数据范围变化 |
| 超级管理员纠正 | 新提交 + `correction_of_commit_id` |

登录、查询、查看详情等只读行为默认不进入字段变更表；如果要做安全审计，可继续写入单独的访问日志，避免污染变更列表。

### 8.3 事务和一致性

一次写入必须尽量在同一个数据库事务中完成：

1. 锁定或读取目标记录当前版本。
2. 校验操作者权限和请求中的 `expected_version`。
3. 重新计算差异，防止客户端伪造旧值。
4. 更新业务表。
5. 更新 `record_versions` 或业务表 `data_version`。
6. 写入 `change_commits`。
7. 批量写入 `change_items`。
8. 成功提交事务。

若审计记录写入失败，推荐整个业务写入失败并返回可重试错误，避免出现“数据改了但无证据”的情况。对大批量导入可采用事务分块，但每个已提交分块必须有清晰的批次关系和结果状态。

### 8.4 不信任客户端提交的旧值

前端可以带 `expected_version` 作为并发控制提示，但 `old_value` 必须由后端从数据库读取并计算。服务端不能直接相信前端提交的“修改前值”，否则用户可以伪造历史或绕过冲突检测。

## 9. API 计划

所有接口继续使用现有 `/api/v1` 前缀和 `{ code, message, data }` 响应封装。

### 9.1 变更查询

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /admin/audit/changes` | 管理员及以上 | 查询当前角色有权看到的字段变更行 |
| `GET /admin/audit/commits/:commitId` | 管理员及以上 | 查看一次提交的详情和字段差异 |
| `GET /admin/audit/records/:targetType/:targetId/history` | 管理员及以上 | 查看目标记录版本时间线 |

普通管理员的查询结果由服务端按权限过滤，不依赖前端隐藏菜单。

### 9.2 纠正和恢复

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `POST /super-admin/audit/commits/:commitId/correct` | 超级管理员 | 根据一次提交发起字段级纠正 |
| `POST /super-admin/audit/records/:targetType/:targetId/restore` | 超级管理员 | 恢复目标记录的指定历史字段 |


`force_on_conflict` 不建议默认开放；如果允许超级管理员强制覆盖，也必须二次确认并在差异明细中标记 `overridden`。

## 11. 关键安全与治理要求

### 11.1 审计记录不可篡改

最低要求：

- 审计表不提供普通业务删除接口。
- 超级管理员也不能通过普通页面删除或修改历史提交。
- 纠正、恢复和管理员权限调整一律写新提交。
- 记录账号删除后仍保留操作者 ID 和名称快照。
- 审计表设置按 `created_at`、`operator_id`、`target_type + target_id`、`field_name` 的索引。

增强要求：

- 对提交内容计算摘要，保存 `prev_hash` 和 `commit_hash`，形成可校验的追加链。
- 定期将审计摘要写入受保护的备份介质或对象存储。
- 记录审计数据的访问行为，尤其是明文敏感字段查看和导出。

### 11.2 权限必须服务端强制执行

前端隐藏按钮只能改善体验，不能作为安全边界。后端每次查询和纠正都必须重新检查：

1. 当前操作者角色。
2. 当前管理员层级和授权范围。
3. 目标记录是否在可操作范围内。
4. 字段是否允许查看或编辑。
5. 纠正者是否为超级管理员。

### 11.3 防止敏感数据泄露

- 审计列表默认只返回脱敏值。
- 不在 zap 日志、请求日志或错误信息中打印 old/new 原值。
- 不记录密码、密码哈希、令牌和验证码。
- 纠正接口不接受客户端传入的 `old_value` 作为可信依据。
- 访问审计接口继续使用限流和请求 ID。

## 13. 测试与验收标准

### 13.1 功能验收

1. 管理员编辑一名校友的 3 个字段后，审计列表准确出现 3 行。
2. 未发生变化的字段不生成差异行。
3. 审计行能准确显示操作者、角色、管理员类型、目标、字段、旧值、新值和时间。
4. 同一次保存产生同一个提交编号。
5. 批量导入能区分新增、修改、跳过和失败记录。
6. 超级管理员可按子管理员、字段、目标和时间筛选。
7. 超级管理员可以只纠正一个字段，不影响同一记录的其他字段。
8. 纠正操作产生新的提交，并链接到原提交。
9. 原提交仍然可查，不能被编辑或删除。
10. 目标在纠正前已被其他人继续修改时，系统阻止静默覆盖并提示冲突。
11. 管理员账号停用后，其历史变更仍可按原姓名和账号查询。

### 13.2 权限验收

1. 普通管理员不能查询未授权的其他管理员审计记录。
2. 子管理员不能调用超级管理员纠正接口。
3. 前端隐藏按钮后，直接调用接口仍然得到 403。
4. 无权限用户不能查看敏感字段明文。
5. 不能通过接口修改或删除审计历史。

### 13.3 一致性验收

1. 业务数据更新成功时，字段级审计必须同时成功。
2. 审计写入失败时，业务更新回滚或进入明确的失败状态，不能产生无审计数据。
3. 并发编辑同一校友时，至少一个请求得到版本冲突，而不是互相覆盖且都显示成功。
4. 纠正后再次查询校友详情、校友列表和数据大屏，数据保持一致。
5. 重试同一个带幂等键的请求不会生成重复提交。

### 13.4 性能验收

- 审计列表常用筛选在现有数据规模下满足管理端可接受的响应时间。
- 复杂筛选使用数据库索引，不在 Go 内存中全量扫描。
- 批量导入不会因一次性构造过多差异导致 API 超时；必要时采用异步任务。
- 版本时间线只加载目标记录的历史，不读取全量审计表。

## 14. 风险与取舍

| 风险/取舍 | 处理建议 |
| --- | --- |
| old/new 值会增加存储量 | 只存实际变化字段；批量导入分批；长期数据按策略归档 |
| 敏感字段可恢复意味着必须保护历史值 | 应用层加密、权限分级、明文查看审计；绝不写入日志文件 |
| 现有 repository 更新接口只返回错误 | 需要调整为返回更新前后快照或由 service 在事务中读取并计算 |
| `operation_logs` 与新审计模型重复 | 保留通用操作日志，新模型作为字段级事实来源，避免一次性破坏兼容功能 |
| 整批回滚容易覆盖后续正确修改 | 默认按目标、按字段选择恢复，并做版本冲突检测 |
| 管理员层级可能逐步复杂化 | 先用直属上级 + 字段白名单；需要复杂组织时再独立关系表 |
| 统计图表可能掩盖具体错误 | 差异行和提交详情为主，图表只做汇总和导航 |
| 允许超级管理员强制覆盖会带来高风险 | 默认禁止强制覆盖；开放时必须填写原因、二次确认并标记覆盖状态 |

## 15. 评审时需要确认的产品决策

请优先确认以下 6 点，确认后即可据此进入详细设计：

1. 是否采用“修改立即生效，超级管理员事后查看并纠正”的默认模式？如果需要先审批，方案会增加 `pending/approved/rejected` 流程。
2. “主管理员”和“子管理员/副管理员”是否需要不同的实际权限，还是只需要上下级关系和审计归属？
3. 子管理员的数据范围是否按全部校友处理，还是需要限制到指定年级、班级或其他条件？
4. 子管理员能否修改姓名、年级、班级等基础字段，还是只允许修改工作信息和联系方式？
5. 手机号、邮箱、通讯地址的历史值，超级管理员是否可以查看明文，还是始终脱敏？
6. 批量导入是否要求“一个 Excel 文件对应一个提交”，并支持按行选择性恢复？

## 16. 本次评审建议重点

建议先不讨论字段名和接口路径的细枝末节，优先确认三件事：

- 变更是否立即生效。
- 管理员是否存在真正的权限层级和数据范围。
- 超级管理员纠正时，是恢复旧值，还是直接输入正确的新值。

这三项决定了后续数据库模型和页面交互；其余字段、颜色、图表和接口命名可以在原型评审阶段快速调整。
