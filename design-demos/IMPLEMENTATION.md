# 多段学籍开发交接

设计需求：[Issue #236](https://github.com/JunLang-7/sduzg-alumin-platform/issues/236)。交互参考：[当前原型](alumni-education.html)。

本原型已由用户确认，作为开发参考保留在不合并的 Draft PR 中。正式开发需另建实现 Issue，写清接口、迁移、权限及验收条件，从当时最新的 `main` 建立功能分支，引用本设计 PR。不要把本原型分支合并或直接改成业务功能分支。

## 已确认的页面行为

| 场景       | 确认的行为                                                                     |
| ---------- | ------------------------------------------------------------------------------ |
| 校友详情   | 保留原有视觉和详情表格；顶部校友档案只放个人信息                               |
| 多段学籍   | 本科、硕士、博士可同时存在，同层次也可多段；全部完整展示，无折叠               |
| 学籍档案   | 各段分别展示自己的学籍信息、学位档案和学籍档案                                 |
| 查看与编辑 | 查看页无添加、编辑、上传、移除等修改入口；从列表的“编辑”打开原有形式的编辑弹窗 |
| 编辑结构   | 个人信息、学籍与档案两个分区；个人信息维护一次，每段学籍独立维护字段和附件     |
| 保存与取消 | 修改先保存在草稿中；保存全部修改后生效；取消、关闭、Escape不保存               |
| 操作历史   | 管理员详情页底部保留，能定位到个人信息或某段学籍及修改前后值                   |
| 新增学籍   | 在编辑表单里添加，可移除本次尚未保存的新增段；本原型未增加删除既有学籍流程     |

## 字段归属

| 归属         | 字段                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| 校友个人信息 | 姓名、性别、手机号、邮箱、行业、工作单位、职务、通讯地址                      |
| 每段学籍     | 培养层次、培养类别/管理数据域、年级、班级、届数、专业、培养方式、辅导员、导师 |
| 学籍内部维护 | 管理员备注、该段的学位档案和学籍档案                                          |

培养层次表达本科、硕士、博士；现有本科生、学术学位研究生、MPA数据域继续用于管理员授权，二者不要混为一个字段。学号、学位取得情况等额外字段不是本次已确认界面的必填项；是否新增应在实现 Issue 中明确。

## 建议的数据结构与迁移方向

以下是实现建议，尚未确定表名、接口或迁移方案。

- 保留稳定的个人身份标识，账号绑定个人身份；一份个人档案关联多段学籍。
- 将年级、班级、专业、导师等字段及管理数据域迁至学籍记录。文件关联具体学籍及文件类别。
- 操作历史能关联人和可选学籍；既有日志必须有兼容展示方案。
- 旧档案可先逐条迁移成一人一段学籍，再由有权限的人员处理重复身份。不能仅凭同名、手机号相同自动合并；无法可靠推断的培养层次等字段保留待核验。
- 处理既有账号绑定、文件归属、管理员备注和导入导出去重逻辑，不能只替换详情页。

## 权限与现有规则

正式实现需要继续使用仓库现有“角色 + 数据域 + 功能权限”，由服务端执行授权。

- 游客不可访问校友个人资料；校友端仅访问本人资料和学籍，沿用已有可修改字段与认证流程，不开放管理员管理入口。
- 管理员只能读取或维护授权学籍；不能因能访问某个人就读取其其他域的学籍、附件、内部备注或数量。
- 个人敏感字段继续受现有功能权限控制；共享个人信息的写入与审计可见规则须在实现 Issue 中明确，不能把原型中预设有权限的管理员视角推广为全部管理员权限。
- 已有学籍不能通过普通编辑接口迁移数据域。各段附件的上传、下载、删除及审计均需独立校验角色、功能权限和学籍数据域。
- 个人档案联系方式更新，不应隐式改变登录凭据；需沿用现有联系方式验证接口及绑定规则。
- 原型把管理员备注放在对应学籍内，避免跨域共享内部备注；历史单条备注如何迁移需明确。

原型会演示共享个人信息历史对有相应权限的管理员可见。这是展示假设，正式系统仍须确定审计敏感信息的脱敏及权限规则。

## 实现前需要确定

1. 表结构、文件学籍外键、账号关联、旧日志兼容、迁移与回退方案。
2. 详情、列表、本人资料、编辑提交和文件接口的DTO兼容策略；列表一人一行，学籍筛选条件必须匹配同一段。
3. “保存全部修改”的事务及并发控制：校验失败不能部分更新；多名管理员编辑同一人时不能静默覆盖别人的改动。
4. 文件草稿暂存、取消清理、保存提交及失败恢复，确保取消不触发正式文件删除或产生孤立附件。
5. 个人信息和学籍的写入权限、共享信息审计范围，以及历史重复人员的人工核验流程。
6. 统计口径：校友人数按人去重，学籍按段统计，分层次人数相加可能大于总人数。

## 实现阶段验收建议

- 正常路径：一人多段本硕博、同层次两段学籍、独立附件、统一保存与历史前后值。
- 取消与失败：关闭/取消不落库，字段校验、保存失败、文件失败和并发冲突不造成部分更新。
- 权限边界：未登录、非本人、跨数据域、缺敏感字段/文件/审计权限均不泄露信息或数量。
- 历史兼容：现有账号、学籍字段、文件和日志迁移后可追溯；导入、导出、搜索及大屏不重复计人。
- 按仓库约定补后端、前端、迁移集成测试，运行 `make check` 及相关 Compose E2E。

## 原型验证的范围

30项浏览器交互检查已覆盖当前设计的只读完整展开、编辑弹窗、草稿取消/关闭/保存、必填校验、同层次多段学籍、操作历史、数据域展示和窄屏。原型没有调用业务API；这不是数据库事务、真实认证授权、文件存储或正式应用E2E的验证结果。
